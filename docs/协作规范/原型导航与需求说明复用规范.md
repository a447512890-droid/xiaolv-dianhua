# 待办电话原型导航与需求说明复用规范

## 1 文档用途

本规范把一个旧原型项目中的导航、页面模块拆分、说明数据外置、响应式和验收方法改写为待办电话项目可采用的参考。当前原型已位于 `原型/`，文中的早期建议须服从最新用户决定，也不要求复刻旧项目的双语手机对照和右侧说明面板。具体原型布局应根据待办电话的实际评审方式重新确定。

## 2 待办电话原型的建议页面结构

建议以用户任务流组织页面，而不是照搬摄像头项目的版本树：

```text
待办电话
├── 需求与概览
│   ├── 产品概念
│   ├── 功能清单
│   └── 决策流程
└── 产品流程
    ├── 客户列表/客户详情
    ├── 拨打前客户上下文
    ├── 通话中客户沟通看板
    ├── 通话后总结与转录
    ├── 沟通重点与情绪回顾
    ├── 待办详情
    └── 待办与沟通历史
```

正式页面键须在原型实现时确认。本文件中的结构是建议，不是既成导航。

## 3 信息架构与主流程

核心闭环：

```text
选择/匹配客户
  → 拨打前回顾资料、最近沟通、承诺和待办
  → 通话过程中查看客户沟通看板
  → 获取或导入通话内容
  → 生成转录、沟通重点和决策分析
  → 用户核对客户状态；明确约定自动创建待办
  → 保存沟通记录，未完成待办可编辑，完成后仅可删除
  → 下次联系前回顾上次结果
```

边界：

- 当前不预设 iOS 普通电话可被本 App 无感采集。
- 通话内容也可能来自导入音频、用户录入的文字或语音；实际首发方式待确认。
- 模型识别结果应显示依据，客户字段由用户确认后更新；明确约定的行动项自动创建为待办，创建后可编辑。
- 与 iOS 提醒事项的连接是可选方案，不能让用户未授权时失去 App 内任务能力。

## 4 通用页面导航设计

当前产品导航按“沟通／通讯录／待办／记录”组织。下表为早期任务流建议，不能覆盖实际标签页导航：

| 分组 | 页面建议 |
|---|---|
| 准备 | 客户列表、客户资料、拨打前上下文 |
| 沟通 | 通话中客户看板、通话状态/结束状态 |
| 复盘 | 转录、沟通重点、情绪回顾、决策进展 |
| 跟进 | 待办详情、待办列表、客户沟通历史 |
| 文档 | BRD、功能清单、App Store 元数据、流程说明 |

导航只承担页面跳转和层级提示，避免塞入大段业务说明。页面名称、模块键和路由一旦接入代码，应保持唯一并同步维护。

## 5 模块需求说明规范

### 5.1 核心原则

按具体 UI/交互模块拆分需求，不用一条说明概括整页。示例：拨打前页面可分别说明客户摘要、最近沟通、未完成承诺和待办；通话后页面可分别说明转录、沟通重点、决策分析和行动项。

### 5.2 推荐字段

当前项目 `docs/产品需求/需求说明.md` 采用七个字段：

| 字段 | 编写要求 |
|---|---|
| 标题 | 模块短名称 |
| 模块说明 | 用户可见能力或模块用途 |
| 数据来源 | 明确来自客户资料、转录、用户输入、模型或系统服务；未确定则标记待确认 |
| 前置条件 | 登录、客户关联、授权、输入数据或状态条件 |
| 后置结果 | 用户操作后可观察到的数据或页面状态 |
| 显示数量限制 | 条数、字符数、时长、文件大小等；未知标记待确认 |
| 排序规则 | 时间、优先级或固定次序；未知标记待确认 |

### 5.3 编写边界

- 每个模块说明只覆盖一个逻辑区域。
- 区分已确认规则、实现方案和待确认问题。
- 不把宣传语当作可验收的需求。
- 不凭空确定 API 字段、保留期限、模型准确率、金额或数量限制。
- AI 判断说明证据、时间位置和不确定性；没有证据时应允许不判断。
- 行动项根据明确约定自动创建为待办；区分“待完成”和“已完成”，允许编辑并保留来源依据。
- 情绪分析描述表达线索，不做医学诊断或人格判断。
- 页面中的姓名、公司、金额、日期等样例须标为演示数据，不使用真实个人客户信息。

## 6 建议数据结构与页面映射

需求说明 Markdown 可使用模块键作为主键。原型实现时，在代码中单独映射页面、稳定选择器和模块键，不把 DOM 选择器塞进 Markdown。

```js
const moduleNoteTargets = [
  ['call-prep', '[data-module="customer-context"]', 'callPrepCustomerContext'],
  ['call-live', '[data-module="customer-board"]', 'callInProgressBoard'],
  ['call-review', '[data-module="action-items"]', 'callActionItemExtraction']
];
```

上述路由/选择器只是示例。真实映射必须按实现 DOM 更新，选择器需唯一、稳定，优先使用 `data-*` 属性。

推荐页面数据标识：

- `call-prep`：拨打前上下文
- `call-live`：通话中看板
- `call-review`：转录与沟通重点
- `action-confirm`：待办详情
- `follow-up`：待办和历史回看

正式命名待原型信息架构确认后统一。

## 7 AI 结果在原型中的呈现

通话后分析卡建议展示：

1. 结论/标签，如意向状态或购买阶段。
2. 依据：客户原话、说话人、时间位置。
3. 不确定性：已确认、推测或待确认。
4. 用户操作：确认、修改、忽略或补充信息。
5. 后续动作：客户字段经用户确认后更新；明确约定自动创建为待办，创建后可编辑。

示例行动项卡：

```text
建议行动：周五发送正式报价
负责人：我方销售（若转录明确）
依据：“我周五把报价发给您。” · 00:42
[编辑待办] [标记完成] [查看来源]
```

若时间、负责人或承诺对象不明确，应留空并提示确认，不从上下文擅自推算。

## 8 视觉与交互原则

- 视觉风格以待办电话产品自身设计系统为准；本规范不要求照搬旧项目的青绿配色、固定栏宽或手机尺寸。
- 重要内容按通话前、通话中、通话后分层，保证通话中看板在有限屏幕上快速可扫读。
- 标签状态除颜色外，同时使用文字或图标。
- 主要操作使用清楚的按钮和可读状态，支持键盘/辅助技术（适用时）。
- 处理录音/转录时，录制状态、授权状态及保存状态需清楚可见。
- 对分析结果提供原文回看能力，避免让用户只看到不可解释结论。
- 响应式布局按实际目标设备制定；不得直接套用旧项目 264px/312px 导航栏尺寸。

## 9 可访问性、隐私和安全

- 按钮、切换项和状态需具有清楚的可访问标签。
- 不用颜色作为唯一状态表达。
- 动效应尊重系统减少动态效果设置。
- 需求说明和原型样例中不得出现真实通话内容、客户号码、访问令牌或生产密钥。
- 原型样例使用虚构姓名和公司，并标注“示例数据”。
- 如通话音频或转录发送到第三方服务，需明确显示处理对象、用途、保存方式和用户控制选项；产品合规细节需另行核实。

## 10 验收清单

### 信息架构与导航

- [ ] 页面结构体现客户沟通主闭环，导航名称与实际页面一致。
- [ ] 页面键和模块键唯一，页面间跳转可用。
- [ ] 通话前、通话中、通话后状态不混淆。

### 需求说明

- [ ] 每个说明点对应一个清晰模块。
- [ ] 七个字段齐全；未知值明确标记待确认。
- [ ] Markdown 的模块键与原型映射一致。
- [ ] 删除或新增模块后同步维护映射和说明数据。

### AI 与待办

- [ ] 重点、决策阶段、情绪和行动项有原文依据。
- [ ] 模型推测与客户明确表述区分清楚。
- [ ] 无明确证据时可返回未判断/待确认。
- [ ] 用户可确认、编辑或忽略模型提议。
- [ ] 明确约定自动创建待办，无需确认创建；创建后可编辑；待办包含空状态与有待办状态。
- [ ] App 内任务在系统提醒授权缺失时仍可使用（若采用建议方案）。

### 隐私与交互

- [ ] 通话数据采集状态、授权和保存方式有明确说明。
- [ ] 样例数据为虚构，不泄露个人信息。
- [ ] 交互适配目标设备，重要内容不被裁切。
- [ ] 已检查关键流程的空状态、失败状态和长内容状态。

## 11 接入步骤

1. 确认首发目标用户、电话采集方式和核心流程。
2. 固化页面信息架构、状态和路由标识。
3. 在 `docs/产品需求/需求说明.md` 中维护已确认的模块字段。
4. 建立稳定的页面/模块键与 UI 选择器映射。
5. 先实现拨打前上下文、通话后整理、待办详情这条最小闭环。
6. 再加入通话中看板、决策分析、情绪回顾和系统提醒同步。
7. 按上方验收清单检查，并将尚未真实接入的能力明确标记为演示或待开发。

## 模块说明入口样式

原型模块使用右上角动态波纹圆点作为说明入口，不显示“需求说明”文字。默认青色，当前选中模块为蓝色；点击后定位右侧模块说明，小屏幕打开说明面板。圆点保留可访问名称与键盘焦点，减少动态效果设置下停止波纹动画。
